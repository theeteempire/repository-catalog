# Repository Catalog

> **Discover. Explore. Stay updated.** A refreshed catalog of PS5 payloads and repositories, with concise metadata, categories, source links, and change tracking.

## ✨ Catalog highlights

- **PLDMGR display format:** `⭐ stars · 📥 downloads · 🕒 short date | original description`. Preserve the payload-specific description; do not append a separate Firmware field.
- **Popularity and freshness:** Use real GitHub star counts, release-asset download counts when available, and update dates without inventing missing metrics.
- **Compatibility clarity:** Include compatibility notes only when supported by source evidence, within the original description rather than as a separate display field.
- **Integrity and validation:** Validate catalog structure, direct HTTPS ELF links, icon mappings, and upstream checksums when supplied.
- **Categories and discovery:** Organize entries by category and discover eligible public repositories through configured sources.
- **Change tracking:** Publish a machine-readable changelog of additions, updates, and removals after a successful catalog refresh.
- **Community context:** Keep GitHub stars distinct from user ratings. Community reviews require a reliable review source and are not fabricated.

![Repository Catalog automation overview](assets/catalog-flow.svg)

Repository Catalog is an automated data-collection and change-monitoring tool for configured public online sources, with a focus on repository metadata and eligible downloadable payload assets. It periodically checks configured source feeds and public GitHub repository/release information, compares discovered records with the existing catalog, validates the results, and publishes structured JSON feeds for monitoring and downstream data-processing workflows. It monitors only sources reachable through its configured feeds and discovery criteria; it does not crawl the entire internet.

The goal is to provide a regularly refreshed, organized view of repository and asset information without requiring every entry to be maintained manually. The catalog is an index of publicly available data; it does not modify source repositories or independently certify the safety, quality, or compatibility of indexed files.

## Published data

The generated `payloads_v2.json` feed keeps the payload-specific text in `original_description`; its display `description` follows `⭐ stars · 📥 downloads · 🕒 short date | original description`. Missing metrics are shown as `Unknown`, and a separate Firmware field is not appended to the PLDMGR display line. Compatibility notes remain in the original description only when supported by source evidence. The generated `changelog.json` records additions, updates, and removals from the latest successful comparison.


The workflow publishes these JSON files:

| File | Purpose |
|---|---|
| [`payloads_v2.json`](https://theeteempire.github.io/repository-catalog/payloads_v2.json) | Structured records for eligible downloadable payload assets, including direct HTTPS links where available |
| [`repositories.json`](https://theeteempire.github.io/repository-catalog/repositories.json) | Repository records and available metadata |
| [`icons.json`](https://theeteempire.github.io/repository-catalog/icons.json) | Icon metadata referenced by catalog records |

These feeds can be consumed by compatible clients, dashboards, and data-processing tools. The collection scope is determined by the configured source lists, search criteria, and validation rules used by the workflow.

## How the automation works

The catalog is generated by GitHub Actions. It runs every six hours and can also be started manually.

![Catalog workflow diagram](assets/catalog-flow.svg)

1. **Collect source data.** Read configured repository databases and curated asset feeds.
2. **Discover repositories.** Search public repository metadata using the workflow's configured discovery criteria.
3. **Filter and merge.** Skip archived or unsuitable records, and avoid adding repository URLs that are already indexed.
4. **Inspect releases.** Check repository releases for eligible individual `.elf` assets and record direct download URLs when available.
5. **Track changes.** Compare newly collected records with the existing catalog, preserve first-seen information, and refresh supported version/update metadata when sources change.
6. **Normalize records.** Deduplicate entries, assign stable unique IDs, apply categories, and connect available icons.
7. **Validate output.** Check the generated JSON, icon mappings, and direct asset URLs before publishing the refreshed catalog.

This process can discover additional public repositories during future runs without requiring each entry to be added manually.

## Community and freshness metadata

Generated repository and payload records may include these optional fields:

| Field | Meaning |
|---|---|
| `github_stars` | Current public GitHub star count for the originating repository; a popularity signal, not a 5-star quality rating |
| `download_count` | GitHub's reported download count for the exact release asset used by the catalog URL, when available |
| `download_count_source` | Identifies the source of the count (`github_release_asset`) |
| `open_issues_count` | Public open-issue count from the originating repository; it is not a review count |
| `repository_updated_at` | Repository push/update timestamp reported by GitHub |
| `last_update_days` | Age in days calculated from the record's existing `last_update` date |
| `last_update_months` | Approximate age in months calculated from the same date |

These are additive fields: the existing schema version and required payload fields remain unchanged so consumers that ignore unknown JSON fields can continue to parse the feed. Metrics are omitted when GitHub does not expose reliable data; the workflow does not invent download counts or dates.

The catalog currently has no trustworthy, standardized per-payload user-review source. GitHub stars must not be presented as a rating out of five, and issue counts must not be presented as review counts. A genuine star rating and concise opinion summary require a supported review/discussion source and a client UI that explicitly displays those fields. This repository publishes data feeds rather than a standalone interactive catalog page, so fields added here will not automatically appear in a PLDMGR screen unless that client supports rendering them.

## Asset inclusion rules

The payload feed focuses on direct HTTPS links to individual files ending in `.elf`. A repository URL, release page, or ZIP/archive download is not treated as a direct asset link.

Some projects distribute files only inside archives, publish assets outside supported release pages, or do not publish downloadable assets. Such projects may still appear in the repository index but will not be included in the direct-download feed unless a suitable asset can be identified.

The generator avoids inventing metadata. It does not fabricate version numbers, checksums, release tags, or download URLs. A checksum is included only when an upstream source provides one.

## Available metadata and quality checks

Depending on the source data, a record may include:

- **Name and filename** — a human-readable label and asset filename.
- **Download URL** — a direct HTTPS URL to an asset.
- **Source information** — the associated project or repository.
- **Description and category** — context for organizing records.
- **Version and last update** — when supported by the source.
- **Checksum** — only when supplied by an upstream source.
- **Icon reference** — included when a matching icon is available.

Build-time checks help detect duplicate asset identities, repeated IDs, invalid icon references, malformed JSON, and invalid direct asset URLs. Records that fail required validation should not be published.

## New-entry labels

Newly discovered entries can be marked with `· NEW` in the existing name field for seven days. The generator preserves each entry's `first_seen` date across scheduled runs. Routine version changes to known entries are not treated as new discoveries.

## Categories and icons

Records are assigned categories to make the feed easier to browse. Existing curated icons are preferred where available. If no suitable curated icon exists, the catalog may use a normalized avatar from the repository owner's profile as a fallback. A fallback avatar is not presented as the project's official logo.

The icon feed is keyed by SHA-256 hashes. The scheduled workflow rebuilds `icons.json` along with the catalog, pulling the configured upstream icon feed and generating fallback repository-owner avatars when needed. Changes are published when the workflow succeeds. The published JSON uses an absolute GitHub Pages URL for `icons_url`, allowing clients to resolve icons without relying on relative paths.

## Sources and discovery scope

The catalog combines upstream community data with automated discovery through the GitHub Repository Search API. The exact collection scope depends on the source lists and search terms configured in the project. Search results may vary with repository names, descriptions, README content, indexing, and API limits.

Finding a repository does not automatically mean that it has a valid downloadable asset to publish. Private repositories are not included in public discovery.

## Automatic updates

- **Schedule:** Every six hours. Each successful run recollects supported source data and regenerates the repository, payload, and icon JSON feeds. The SVG illustration is static and changes only when the image file is edited.
- **Manual run:** Open [Actions](https://github.com/theeteempire/repository-catalog/actions), select the catalog update workflow, and choose **Run workflow**.
- **Authentication:** The workflow uses GitHub Actions' built-in `GITHUB_TOKEN` for normal operation.
- **Publishing:** Generated files are validated before being committed; GitHub Pages then serves the public JSON feeds.

Check the [latest workflow runs](https://github.com/theeteempire/repository-catalog/actions) to see whether the most recent update succeeded.

## Limitations

Automated discovery cannot guarantee complete coverage. Some repositories may not appear in search results, and some releases may not provide individually downloadable assets or use a distribution method the generator can interpret. Updates may also be delayed if GitHub's API or an upstream source is temporarily unavailable.

A direct download link does not guarantee that a file is safe, maintained, or suitable for a particular environment. Review the original project's documentation and release notes before using any downloaded asset. This catalog organizes public project data; it does not modify asset binaries or independently audit their contents.

Contributions are welcome. You can report missing entries, suggest improvements to discovery criteria or validation, or propose changes to the catalog format. Include the original source URL and enough context to explain the proposed change, and avoid unofficial or misleading download links.
